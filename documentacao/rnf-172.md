# Requisitos não funcionais: evidência de 10/10/2026

O requisito histórico RNF002 em review-requisitos.md pede carregamento abaixo de três segundos sob grande volume; não define cardinalidade, concorrência ou percentil. Esta tarefa mede uma amostra local explícita, sem promover a medição da API a tempo de renderização completo de páginas ou SLA de produção.

## Protocolo reproduzível

`npm ci`, `npm run prisma:generate`, `npm run test:logger:disabled` e `npm run test:rnf`. O script RNF exige container de QA deste chat, label de propriedade e binding127.0.0.1:5434. Cria um banco e papel com nomes UUID próprios, aplica migrations somente nele, insere10000itens sintéticos, aquece três consultas públicas e mede30requisições sequenciais e120com concorrência8. Consultas: feed20registros, busca/cidade/UF e página400. Não usa a API7340 compartilhada, não lê .env e não carrega Config.Env do Docker. Remove somente banco/papel criados pela própria execução; falhas de teste ou cleanup produzem exit1 e evidência passedfalse.

`rnf-172-resultado.json` registra hardware agregado/runtime, cardinalidade, duração, CPU, RSS, atraso do event loop, mediana/p95/máximo, erros e limites. A primeira rodada falhou porque a expectativa401 estava incorreta: a fachada atual retorna498 para sessão ausente/inválida. A expectativa foi reconciliada com HttpStatusCodes/createAuthMiddleware; a falha não foi suprimida. Foram reproduzidos Helmet, bloqueio de auth nativa, limite10/15min login e limite300/15min geral, sem mudar proteções.

O teste revelou buffering Winston quando LOG_ENABLED=false e nenhuma saída é instalada. O logger agora fica silent nesse caso, evitando acumular mensagens. Um teste real envia1000mensagens e verifica ausência de backlog após processamento; a configuração padrão com logs ativos permanece intacta.

## Recorrência Docker

Desktop4.74.0/Engine29.4.3 falhou09/10e10/10 em sockets AF_UNIX de Secrets Engine e Inference manager. Em10/10, log confirmou remove dockerInference:error1920/listenerinvalidname. Somente os diretórios de sockets foram preservados por renomeação após confirmar processo parado e entradas0bytesReparsePoint; Engine voltou e container próprio foi iniciado. Nenhum reset, volume removido, prune, diagnóstico enviado ou reboot.

Relatos no tracker oficial apresentam a mesma classe de erro: https://github.com/docker/desktop-feedback/issues/531 e https://github.com/docker/desktop-feedback/issues/625. São relatos, não comprovação de causa de kernel nesta máquina nem release corrigida. Atualizar automaticamente, apagar VHD/volumes ou prometer correção permanente não é justificado por essa evidência. Se reaparecer, registrar versão/log/estado de processo e preservar dados antes de intervenção. Desligamento limpo pelo Docker Desktop reduz encerramento abrupto, mas não foi provado como solução definitiva.
